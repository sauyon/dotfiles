  ### 5. nit — `select(.key != "PATH")` is a one-entry denylist feeding `export`
  
  `system/secrets.sh:30-31`, `system/deploy:274-282`
  
  **I traced the quoting for injection and found none.** `mapfile -t` makes each jq output line exactly one array element; `"${sops_env[@]}"` expands to one word per element with no re-splitting, no glob, and no command substitution; and `export` is a builtin that assigns rather than evaluating. Specifically:
  - a key containing `=` (`{"A=B":"C"}`) → `export "A=B=C"` → sets `A` to `B=C`. No execution.
  - a key that is not a valid identifier (`{"a b":"1"}`) → `export` fails with *"not a valid identifier"*, returns 1, `set -e` aborts deploy. Fail-closed.
  - shell metacharacters or `$(...)` in a *value* → assigned literally, never expanded.
  - the one real caveat: a **newline** in a value splits into an extra array element, so `{"K":"a\nLD_PRELOAD=/evil.so"}` becomes two words and the second is exported as its own assignment. Still a plain `export`, not code execution.
  
  Which leads to the actual (mild) observation: PATH is filtered, but nothing else is. `LD_PRELOAD`, `BASH_ENV`, `IFS`, `GIT_SSH_COMMAND` and friends would all be exported into a shell that goes on to run `nix build`, `sudo`, `systemctl restart`. **This is not an escalation path** — the source is `home.nix` and the pinned flake inputs, and anyone who can change those can change `system/deploy` itself. But the justification given for filtering PATH is that `sops.environment` is written for a *different consumer* (`sops-install-secrets`, sandboxed, PATH="") and therefore may contain entries that are wrong here. That argument applies to the whole attrset, not just PATH. An allowlist (`GOOGLE_*`, `SOPS_*`, `AWS_*`, `VAULT_*`) is the same amount of jq and does not need revisiting when sops-nix adds a key.
  
  ---
  
  ### 6. nit — the netrc value is validated for emptiness and newlines but not for whitespace
  
  `system/secrets.sh:71`
  
  The multi-line guard is correct and the `wc -l` arithmetic is right (`$( )` has already stripped the trailing newline, `printf '%s'` adds none, so a single-line value counts 0). But a prefixed netrc entry can also be corrupted *within* one line: a token containing spaces, e.g. `tok machine evil.example password tok`, produces a syntactically valid netrc with a second `machine` entry, which would make nix/curl hand credentials to a host of the attacker's choosing.
  
  **Attacker model:** requires write access to `secrets.yaml` **and** KMS encrypt permission — i.e. someone who can already rotate the token to a value of their choosing. Genuinely low value; noted only because the guard next to it is one `case "$val" in *[[:space:]]*) refuse;; esac` away from covering it, and the function is otherwise careful about exactly this class of thing.
  
  (Sub-nit in the same line: `[[ $val == *$'\n'* ]]` would do the multi-line check inside bash instead of piping the plaintext to a PATH-resolved `wc`. Marginal, since `sops`/`install`/`jq` are PATH-resolved too.)
  
  ---
  
  ### 7. nit — `SECRETS` defaults to a CWD-relative path, contradicting the file's own stated contract
  
  `system/secrets.sh:54` — `secrets=${SECRETS-../secrets.yaml}`
  
  The header of the same file states: *"every path is an argument -- no function reaches for a location of its own."* `../secrets.yaml` is a location of its own, and a CWD-relative one. It happens to be right because `deploy` does `cd "$(dirname "$0")"` first, but it means sourcing `secrets.sh` from anywhere else silently reads whatever `../secrets.yaml` resolves to from there. `pacman.sh`, which this file cites as its model, genuinely takes `<dir>` as an argument on every function. Making it `install_secret <secrets-file> <key> <dest> [prefix]`, or just passing the repo root the way `sops_env_for` already does, would make the claim true.
