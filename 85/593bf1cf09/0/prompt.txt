  ## B. ERROR HANDLING
  
  **B1 — Important. `system/deploy:37-40`: a pacman failure aborts the entire deploy before any /etc convergence — a robustness regression against dcaecea.**
  `exit 1` in the `||` block kills the script at line 40, so the etc/ copy (`:44-45`), the Bitwarden polkit action (`:50`), the gnome-keyring masking (`:62-64`), the `tss` group add (`:68`), the oomd restart (`:79-80`), `/etc/nix/nix.conf` include + attic netrc + mari builder key (`:100-116`), the nix-daemon restart (`:119`) and the patched tailscaled (`:133-142`) all stop happening. Before this commit, a package problem could not do that. Given the step is "install some packages that are nice to have", warn-and-continue (or running it *after* the /etc steps, accepting A6's pacman-ownership caveat) is the proportionate behavior; aborting the secrets provisioning is not. Nothing here leaves the host *inconsistently* configured in a dangerous way — deploy is idempotent and rerunnable — but it does leave it half-configured and, on a fresh-host bootstrap, quietly much slower.
  
  **B2 — Important. `system/deploy:38`: the hint names one failure mode; most real failures print it anyway, and the `-Sy` rationale is only half right.**
  `sudo pacman -S --needed --noconfirm` reaches that `echo` for every nonzero exit, so all of these print "if it 404'd, run 'sudo pacman -Syu' and retry": db lock held by a concurrent pacman or a pacman hook (`unable to lock database`), the sudo password being refused or timing out (deploy is run interactively as the user; only during `bootstrap` is `99-bootstrap` NOPASSWD in place), no network / unreachable mirror, `/` or `/var/cache/pacman` full, and unresolvable conflicts — note `--noconfirm` takes the *default* answer, which is **No** for "remove conflicting package?", so a host with a conflicting provider installed (the classic being `bluez-utils-compat` vs `system/packages:58` `bluez-utils`) aborts with a conflict error and gets told to run `-Syu`, which will not help. "`pacman -Syu` and retry" is also non-trivial advice on Arch (full system upgrade, possible reboot) to dispense for what may be a lock file.
  Separately, the deliberate omission of `-y` (commit message; `system/deploy:22-25`) prevents a db refresh but does **not** prevent a partial upgrade: `-S` resolves dependencies against the db *as it stands*, and if that db is newer than the installed system — someone ran `pacman -Sy` by hand, or any tool did — installing `fprintd` pulls `libfprint` and whatever newer `glibc`/`polkit`/`dbus` it depends on, upgrading those packages alone. That is a partial upgrade arrived at by a different door, and neither the comment nor the hint mentions it. The comment states the reasoning as settled ("the one way to break an Arch box") when the chosen alternative shares the hazard.
