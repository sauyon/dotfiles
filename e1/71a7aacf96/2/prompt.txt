**1. `/home/sauyon/devel/dotfiles/home.nix:339` — severity: medium. Post-`unlock_time` fall-through prints `3/3 failed attempts`, which is false; the tally is already void.**

The comment says the fall-through exists "so the next single mistake does not re-lock without warning." pam does the opposite. When `check_tally` takes the expiry branch it sets `FAILLOCK_FLAG_UNLOCKED` and returns `PAM_SUCCESS` (`pam_faillock.c:264-265`); `AUTHFAIL` then calls `write_tally`, which invalidates **every** record on that flag (`pam_faillock.c:320-322`) before appending one. So after `unlock_time` elapses the user has a full `deny` budget back, and the next mistake yields 1/3, not a re-lock.

Scenario with the defaults on this host (`deny=3`, `unlock_time=600`, `fail_interval=900`): mistype three times, wait 11 minutes, lock the screen. `left &lt;= 0` so the countdown branch is skipped, `now - latest = 660 &lt; 900` so the stale guard is skipped, and the label shows red `3/3 failed attempts` for ~4 more minutes while nothing is pending. Confirmed by running the extracted script against a synthetic 700s-old 3-record tally: it printed `3/3 failed attempts`. The `fails &gt;= deny` block should suppress output (or reset the count) once `left &lt;= 0`, not fall through.

Same block, minor: pam's expiry test is `latest + unlock &lt; now`, the script's is `left &gt; 0`, so at exactly `left == 0` pam still denies while the label drops the "Locked out" line. One-second window, 5s poll — noted only because it lives in the same branch.

**2. `/home/sauyon/devel/dotfiles/home.nix:275` — severity: medium. `FAILLOCK_CONF` defaults to the host's `/etc/security/faillock.conf`, but hyprlock's lockout is governed by Nix's copy, so the label's thresholds can silently disagree with the policy actually enforced.**

## Findings (1)

**home.nix:285 — medium-low: the justification for `/usr/bin/faillock` contradicts the `CONF` reasoning 3 lines above, and the resulting host/nix split is unguarded.**

The comment says the tally is "written by the host's pam_faillock". For the lock screen it is not: lines 276-282 correctly establish that hyprlock's libpam loads **nix's** `pam_faillock.so` (verified — `strings` on `/nix/store/c7hb…-linux-pam-1.7.2/lib/security/pam_faillock.so` shows its own `etc/security/faillock.conf` and `/var/run/faillock` baked in). So the script reads a tally written by nix's module using the *host's* reader, which resolves both the record layout and the `dir` option from `/etc/security/faillock.conf`.

Concrete failure: set `dir = /var/lib/faillock` in the host conf (the standard CIS hardening for persisting the tally across reboots, since `/run` is tmpfs). Nix's `pam_faillock` keeps writing `/var/run/faillock` (its own conf is untouched), the host CLI now reads `/var/lib/faillock`, and the label silently reports an empty tally — with no diagnostic, because every failure path is `exit 0`. Same class of breakage from a nixpkgs pam bump that changes `struct tally` or `FAILLOCK_DEFAULT_TALLYDIR`; it works today only because host pam and nix pam are both 1.7.2 with byte-identical, all-commented confs (I diffed them).

Fix: `${pkgs.pam-host-chkpwd}/bin/faillock` exists in that same derivation, is version-locked to the module that writes the records, and resolves `dir` from the same conf `optval` already parses. Caveat that may be the real (undocumented) reason for the host binary: nix's `faillock` does `getpwnam()` without host NSS, so on a systemd-homed-only host it would fail where `/usr/bin/faillock` succeeds — if that's the motive, say so in the comment instead. It works on the current host (the user is in `/etc/passwd`; I ran it).
