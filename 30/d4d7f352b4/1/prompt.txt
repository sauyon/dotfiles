## Findings

**Important — `git.nix` fj helper (home.nix:401-427): malformed `keys.json` is a hard failure, not a graceful fallback**
Every other failure path in the script (`fj` unreachable, no `host` parsed, missing `keys.json`, empty token) does `exit 0` with no output, which git treats as "no credential, please prompt" — the intended graceful degradation per the design. But a syntactically-broken `keys.json` (e.g. fj crashes mid-write, disk full, concurrent writers) is *not* guarded: `token=$(jq ... "$keys")` runs under `set -e`/`set -o pipefail` with nothing catching a jq parse failure, so the script exits with jq's nonzero status. I reproduced this directly:
```
$ printf 'protocol=https\nhost=forge.ko.ag\n\n' | ./script get bad-keys.json
jq: parse error: Invalid numeric literal at line 1, column 4
script exit=5
```
Git treats a nonzero exit from a credential helper as fatal and aborts the operation outright (rather than falling through to a prompt), so a corrupted keys.json turns "log in again" into a hard failure on every `git fetch`/`push`/`clone` against forge.ko.ag, with jq's raw parse error bleeding onto the user's terminal. Fix: wrap the jq call so a parse failure degrades the same way as the other cases, e.g. `token=$(... 2&gt;/dev/null) || exit 0`.

**Minor — comment overstates the token shape (home.nix:397-400)**
"it keeps an OAuth access/refresh token pair in keys.json" is only true for `fj auth login`. `LoginInfo` in fj's source (`keys.rs`) also has a plain `Application { token }` variant (from `fj auth add-token`) with no refresh_token/expires_at. The script itself is agnostic to this (it only ever reads `.token`), so there's no functional bug — just a comment that's narrower than reality.

**Minor — `store`/`erase` no-op means a revoked (not merely expired) token has no recovery path via git**
Since `erase` is intentionally a no-op (fj owns the store), if the Forgejo-side token is revoked/invalidated for a reason other than time-based expiry, `whoami`'s refresh check won't fire (`expires_at` hasn't passed), the same bad token gets handed to git every time, and git has no way to signal "this credential is bad, try another" back to fj. Recovery requires a manual `fj auth login` outside of git. This is arguably inherent to the chosen architecture (git delegates all state to fj) rather than a bug, but it's a real gap in the "failure modes" the task asked to check.
