## Findings

**1. `/home/sauyon/devel/dotfiles/home.nix:339` — severity: medium. Post-`unlock_time` fall-through prints `3/3 failed attempts`, which is false; the tally is already void.**

The comment says the fall-through exists "so the next single mistake does not re-lock without warning." pam does the opposite. When `check_tally` takes the expiry branch it sets `FAILLOCK_FLAG_UNLOCKED` and returns `PAM_SUCCESS` (`pam_faillock.c:264-265`); `AUTHFAIL` then calls `write_tally`, which invalidates **every** record on that flag (`pam_faillock.c:320-322`) before appending one. So after `unlock_time` elapses the user has a full `deny` budget back, and the next mistake yields 1/3, not a re-lock.

Scenario with the defaults on this host (`deny=3`, `unlock_time=600`, `fail_interval=900`): mistype three times, wait 11 minutes, lock the screen. `left &lt;= 0` so the countdown branch is skipped, `now - latest = 660 &lt; 900` so the stale guard is skipped, and the label shows red `3/3 failed attempts` for ~4 more minutes while nothing is pending. Confirmed by running the extracted script against a synthetic 700s-old 3-record tally: it printed `3/3 failed attempts`. The `fails &gt;= deny` block should suppress output (or reset the count) once `left &lt;= 0`, not fall through.

Same block, minor: pam's expiry test is `latest + unlock &lt; now`, the script's is `left &gt; 0`, so at exactly `left == 0` pam still denies while the label drops the "Locked out" line. One-second window, 5s poll — noted only because it lives in the same branch.
