  **nit — Lua long-bracket is safe here but by luck, not by construction.** `[[...]]` terminates on the first `]]`. The values come from `hyprctl clients -j | jq -r '.[].address'`, which are `0x`-prefixed hex, so `]` can never appear and the literal cannot be broken out of. Two caveats worth knowing rather than fixing: Lua strips a leading newline inside `[[`, irrelevant for a single-line hex string; and if `addr` were ever empty the expression degrades to `[[address:]]` (see the Critical finding below for why that matters).
  
  **Critical — `hl.dsp.window.close({ window = ... })` is accepted but *never validated*, so "rc=0" does not mean "a window closed."** The author's live check (`hl.dsp.window.close({ window = [[address:0xdeadbeef]] })` → `ok`, rc=0) used a nonexistent address. That proves the expression *parses*; it proves nothing about the selector being honored. I probed the validation boundary:
  
  ```
  hl.dsp.window.cloze({})                                              -> error, rc=7   (name typo caught)
  hl.dsp.window.close({ window = [[address:0xdeadbeef]], bogus = 1 })  -> ok,    rc=0   (unknown KEY silently ignored)
  hl.dsp.window.close({ window = [[nonsense:zzz]] })                   -> ok,    rc=0   (garbage selector silently ignored)
  ```
  
  So only a misspelled *dispatcher path* produces a nonzero exit. A wrong *argument key* (`window` vs. whatever the close dispatcher actually wants) or a wrong *selector syntax* returns `ok` and rc=0. The commit message asserts the legacy syntax "exits 7, and the `|| true` here swallowed it silently" — I confirmed legacy `closewindow address:0xdeadbeef` is indeed rc=7 — but the new form has moved the failure from a *detectable* rc=7 into an *undetectable* rc=0. Nothing in this change establishes that `{ window = "address:0x..." }` actually selects a window. The one line that would have proven it is the one that cannot be proven with a fake address.

  ### Lens 2 — ERROR HANDLING
  
  **Critical (same root as above) — yes, this would fail silently again.** The commit's stated thesis is "the `|| true` swallowed it silently," yet line 2509 still ends in `|| true`.   **No finding — the 5s wait loop is still correct.** `[ "$count" -eq 0 ] && break` under `set -e` does not abort: the failing `[` is a non-final member of an AND-list, which POSIX/bash exempt from errexit, and the list is not the last command in the loop body. Loop semantics are unchanged by this commit.
  
  **nit (pre-existing) — `count` can be non-numeric.** If `hyprctl clients -j` fails mid-loop, `jq 'length'` yields empty and `[ "" -eq 0 ]` is a bash syntax error (rc=2), silently swallowed by the same AND-list exemption, so the loop just burns its full 5s. Not introduced here.
