**1. `home.nix:834` — Important: the new raw-binary passphrase is mangled by the daemon's non-binary-safe pipeline.**
`head -c 32 /dev/urandom` seals 32 *raw* bytes, but the consumer at `home.nix:770` is `PW="$(unseal)"` followed by `printf '%s' "$PW"` (line 773). Bash command substitution silently drops NUL bytes and strips trailing newlines — measured here: a 7-byte input with one NUL and trailing newlines came out as 4 bytes, plus `warning: command substitution: ignored null byte in input`. `gnome-keyring-daemon --unlock` additionally reads a newline-terminated password from stdin. ~22% of enrolments (`1-(254/256)^32`) produce bytes containing a NUL or a `0x0a`, so the passphrase the keyring is actually created with is shorter than the 32 bytes sealed; in the tail case (first byte `0x0a`) it is empty, which makes the change's own headline claim — "the keyring file is useless off this machine" — false, silently. The removed escrow value could not hit this: its ciphertext is 44 bytes of `type:str`, i.e. base64 of 32 bytes, all printable. The seal script's round-trip check can't catch it either, because `cmp` compares files, not what the daemon receives — and there is no case anywhere for the daemon side. Fix: encode (`head -c 32 /dev/urandom | base64` / `od -An -tx1`) so the value survives a shell variable and a line-oriented reader.

**2. `home.nix:839` — Important: a failed round-trip leaves the untrusted blob on disk and has already destroyed the previous enrolment.**
`tpm2_create` writes directly to `$SEAL/seal.pub` / `$SEAL/seal.priv`, so every abort after line 839 (the MISMATCH exit at 849, a `tpm2_load`/`tpm2_unseal` failure under `set -e`, a signal) leaves the new files in place. Verified with stubs: starting from `seal.pub=GOODpub, seal.priv=GOODpriv`, a mismatching `tpm2_unseal` gives exit 1 and the message "not trusting this blob" while the seal dir now holds `NEWpub`/`NEWpriv` — the message is false, and the next daemon start uses that blob. This is exactly the state test case 6 names as wrong ("a half-done enrolment that wrote seal.pub before bailing would leave the daemon unsealing a passphrase the keyring never had"), and it is now unrecoverable, since the previous passphrase is escrowed nowhere. Fix: seal into `$WORK`, verify, then `mv` into `$SEAL`; and extend case 8 to assert the mismatch path is inert, not just its exit code and wording.

**3. `home.nix:814` (and `docs/new-host.md:150`) — Important: `--force` seals but never removes the stale `login.keyring`, so the documented escape hatch leaves a broken keyring.**
The doc offers them as alternatives ("delete the keyring first, or pass `--force` if you have decided to lose it"), and the refusal text at 815-820 reads the same way. But `--force` only skips the guard: the old `login.keyring`, encrypted with the old passphrase, is still there afterwards. A user who follows the doc, runs `gnome-keyring-tpm-seal --force`, then `systemctl --user restart gnome-keyring`, gets a login collection the daemon cannot unlock with the freshly sealed passphrase — unlock prompts return, which is the exact symptom the whole design exists to remove, and the script printed "sealed to … and verified".
